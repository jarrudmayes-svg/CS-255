# CS-255
CS 255: System Analysis and Design Portfolio

##DriverPass Project Summary
The client for this project was DriverPass — a business that wanted to help students prepare for their driving tests. The client asked for a web-based system that would offer online lessons, practice tests and scheduling of behind the wheel training; employees needed to be able to manage reservations, track student progress and control access (roles) based on each user’s role. My business requirements document described what the client wanted and my system design document explained how the proposed system would meet those needs.

##What I Did Well
I did particularly well at turning the client’s requests into clear requirements and linking those to the system design. I thought about how customers would use the system, driving instructors would use it, office staff and administrators would use it etc. UML diagrams helped me explain the processes and relationships of the system visually. I also worked on communicating the design in a way that a nontechnical client could understand.

##What I Would Revise
If I could change one thing about my work it would be consistency and readability of UML diagrams. I would check labels, connections and detail to make sure each diagram supports the written requirements; give more attention to unavailable appointment times and scheduling conflicts so design explains what should happen when a process can’t be completed as expected.

##Understanding and Addressing User Needs
I interpreted the users’ needs by looking at the DriverPass interview transcript and listing out what each user needed to do. I translated those needs into requirements and design elements (appointment scheduling, access to training materials, progress tracking, role-based permissions). User needs need to be considered because software has to support people who will actually use it. A system can work fine but not meet its purpose if its features or processes don’t fit with how people do their jobs every day.

##My Approach to Software Design
I design software by first understanding the problem, users and results. I organize requirements then diagram the functions, structure and interactions of the system. In future projects I would interview stakeholders, use cases and UML diagrams to analyse requirements before development starts; request feedback throughout design process; trace design decisions back to specific requirements. All these strategies would help me find out what information is missing early on so that I can design a solution that fits the client’s goals.
